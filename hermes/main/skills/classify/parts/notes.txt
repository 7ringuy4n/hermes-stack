MULTIPURPOSE NOTES

Classify an explicit request to remember, record, retrieve, change, or remove personal or group information as task_hint=note, task_type=note, skill=notes. Notes may represent plans, errands, ideas, decisions, lists, reminders without automatic execution, reference material, or any other user-defined subject. Do not restrict this route to travel.

Use skill_action=create only when the user asks to save information that is already present in the message (or in quoted/recalled material the host can treat as content). Emit notes as an array. Each item contains the faithful content, an ISO YYYY-MM-DD note_date when the user associates it with a date, otherwise null, and short semantic tags. Preserve each note's user-authored semantic payload without adding category labels, headings, commentary, or decorative prefixes. Identical input must yield stable content so deterministic storage deduplication remains effective. Resolve relative dates from Local now and Timezone. Split a multi-date plan into independently dated items when that improves later date lookup. Do not invent missing dates or details.

When the user asks to find live information on the web and then note it, do not emit skill_action=create with an empty notes array. Prefer a single task_hint=search turn with process_original_message true and persist_gathered_notes true (one instruction that gathers then lets the host persist). Always emit persist_gathered_notes as an explicit boolean: true for gather-then-note (including when that work is scheduled), false otherwise. Do not omit the key. Do not emit a sibling note instruction that would FIFO-split or start a workflow. When scheduling that same gather-then-note work, keep persist_gathered_notes true on the schedule plan and put only the inner search-note work in message/instructions. Listing quality is owned by the notes skill: concrete Title (stack) — Employer rows with https URLs, never aggregate count buckets, and omit openings already saved when prior notes are supplied. Classification itself never claims storage succeeded.

Use skill_action=lookup for questions that explicitly refer to saved notes, a previously recorded plan, or what was noted for a date or topic. Emit note_selector with id=null unless the user supplies a note id, a concise semantic query, resolved date_from/date_to when present, and semantic tags when useful.

Use skill_action=update or delete only for an explicit mutation request. Emit note_selector that identifies the intended note. For update, emit one replacement item in notes with only the user-authorized content/date/tags. Set uncertain=true when the selector may match multiple notes and let the host ask for clarification; never choose an arbitrary note.

The message is a concise response suitable only after the host confirms the database operation. Classification itself never claims that a note was stored, changed, or deleted.
